## Context

Once hosted on GitHub Pages, many people should be able to view the plan and one person edits it. The data (employees, vacations, shifts) is sensitive and must not be publicly accessible, so viewers need authentication. Pages is static, so there is no server to check credentials.

Important: client-side-only "login" on a static site is not real protection, because the data file is downloadable by anyone with the URL. Protection has to come from access control on the host or from the data being unreadable without a key.

## Status

PROPOSAL. Not decided.

## Options

1. **GitHub Pages access control** (private Pages, GitHub Enterprise Cloud): only org members can open the site. Simplest if our plan supports it. Needs verification.
2. **Encrypted data file** served from Pages, decrypted in the browser with a passphrase (Web Crypto, AES-GCM). Data is safe at rest on a public URL; weaker than real auth (shared passphrase, no per-user revoke).
3. **GitHub API with per-user token** reading JSON from a separate private repo. Real per-user access via repo permissions; each viewer needs a GitHub account and token (or OAuth proxy). The editor writes via the same API (commits).
4. **Free-tier hosted backend with auth** (Firebase, Supabase, Cloudflare Access in front of Pages). Real auth and sharing; adds a vendor and moving parts.
5. **Host elsewhere** (e.g. behind company SSO/internal static hosting) instead of GitHub Pages.

## Open questions

- Does our GitHub plan offer private Pages?
- Is a shared passphrase acceptable, or is per-user access/revocation required?
- Is a vendor (Firebase/Supabase/Cloudflare) acceptable for employee data?
- How does the single editor publish changes (commit, API write, export/import)?
