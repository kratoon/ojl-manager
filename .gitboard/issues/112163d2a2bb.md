## Context

The app will be hosted on GitHub Pages so many people can open it. The data (employees, vacations, shifts) is sensitive. Pages is static, so there is no server to check credentials, and every file on Pages is public.

## Decision

- The app is hosted on GitHub Pages as a **static build only**. **No data is ever committed or deployed**: the JSON data file is not in the repository, not in the Pages artifact, and not stored on any server.
- The user **opens the data file from their PC** (file picker or drag and drop) and **saves it back to their PC** (download / File System Access API where available). The data lives only in browser memory for the session. It is **not persisted** anywhere by the app (no localStorage, IndexedDB, cookies or network upload). Reloading the page returns to the empty state.
- Users **share the file among themselves** by their own means (e.g. internal file share, email). Sharing is outside the app.
- Because the data never reaches Pages, **no encryption, passphrases or viewer authentication are needed**. The earlier idea of an encrypted blob with view/edit passphrases is dropped.
- Same file format as before: validated with the zod schema (`src/data/schema.ts`), accessed through the `DataStore` interface (ADR-514da88). Add a file-based `DataStore` (load from picked file, save to download); the localhost dev API store stays for development.

## Consequences

- Real data never enters git or Pages. Nothing sensitive to protect on the host.
- No revocation or rotation problem: access to data equals possession of the file.
- No shared state: two people editing different copies must reconcile by passing the file around. Last saved file wins. Consider a version/`updatedAt` field and a visible "unsaved changes" warning.
- Losing the file means losing the data, and closing the tab discards unsaved edits. The UI should warn before leaving with unsaved changes.
- The file on a user's PC is as sensitive as before; protecting it is the users' responsibility.
- The view/edit display modes (ADR-e8f59ca) are no longer a security boundary and need revisiting: with a local file everyone can edit their own copy. Hosted default `view` makes less sense, since opening a file is the whole point.
- All "hosted edit unlock" questions in ADR-e8f59ca / ADR-514da88 are resolved by this ADR.

## Open questions

- Should hosted mode be `edit` by default (everyone edits their own in-memory copy), or keep `view` unless a toggle is used?
- Save mechanism: File System Access API (Chromium only, can overwrite the same file) with download fallback?
- Add a file version/`updatedAt` to detect opening an older copy?

## Acceptance Criteria

- [ ] Decision accepted: static Pages hosting, data only via open/save on the user's PC, never persisted
- [ ] Display modes on hosted app decided (see open questions)
- [ ] Save mechanism chosen
