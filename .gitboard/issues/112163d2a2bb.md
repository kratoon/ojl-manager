## Context

Once hosted on GitHub Pages, many people should be able to view the plan and one person edits it. The data (employees, vacations, shifts) is sensitive and must not be publicly accessible, so viewers need authentication. Pages is static, so there is no server to check credentials.

Important: client-side-only "login" on a static site is not real protection, because every file is downloadable by anyone with the URL. Protection must come from the data being unreadable without a key, i.e. encryption.

## Answers so far

- GitHub Pages does not offer private Pages for us. Host-level access control is ruled out.
- A shared passphrase is acceptable for viewing.
- Editing needs a different passphrase (can also be shared). At least two passphrases are required: **view** and **edit**.
- Built in-house, for internal use. No third-party vendor/backend (Firebase, Supabase, Cloudflare Access) is wanted.

## Status

PROPOSAL. Direction chosen, details not decided.

## Direction: encrypted data on Pages, two passphrases

- Data is published as an **encrypted blob** (Web Crypto, AES-GCM). Key derived from the **view passphrase** with a slow KDF (PBKDF2 with high iterations, or Argon2 via WASM). The app decrypts in the browser. Plaintext never goes to Pages or into git.
- **Edit passphrase** gates writing. Open design choice for how:
  - **A. Edit via GitHub API:** the edit passphrase decrypts a fine-grained, repo-scoped GitHub token (stored encrypted); the editor saves by committing a re-encrypted blob, which redeploys Pages. Edit happens in the hosted app.
  - **B. Edit locally, publish by script:** the editor runs the app on localhost against the gitignored local file (ADR-514da88) and a publish script encrypts and commits. The edit passphrase is then only a UI gate (not a security boundary) or is replaced by repo write access.
- Recommended starting point: B for the MVP (no token in the repo), revisit A if editing from the hosted app is needed.

## Risks to accept or mitigate

- The ciphertext is public and permanent in git history. Anyone can brute-force it offline, so passphrases must be long (diceware-style) and the KDF slow. Rotating a passphrase does not protect old published versions.
- A shared passphrase cannot revoke one person; revoking means rotating the passphrase and re-encrypting.
- File sizes, update times and the existence of the data are visible even though contents are not.
- Under A, the encrypted token is a high-value target; scope it to this repo only, contents write.

## Open questions

- A or B for editing?
- Is the repo itself public or private? (Pages output is public either way.)
- Passphrase policy and rotation process?
- KDF choice (PBKDF2 vs Argon2 WASM)?
