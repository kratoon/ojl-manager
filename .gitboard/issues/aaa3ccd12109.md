## Context

Rules currently answer yes/no: may this employee work this shift. We want the engine ready for preferences, so an assignment gets a **score** instead of a boolean. Fairness (similar total shifts for everyone) must be part of that score, so preferences can never create large differences in shift counts. This amends the "all rules are hard constraints" wording of ADR-86a9b67 and replaces the separate fairness ordering step of ADR-4a9d8da.

## Proposal

### Scale: 0 to 10
- A verdict is a number from **0 to 10**. **0 = cannot be assigned** (today's "no", always a hard block). Above 0 = allowed, higher is more preferred. **5 is neutral.**
- 0 to 10 was chosen over 0 to 5 because fairness needs resolution: with 5 as neutral, every shift an employee is ahead or behind moves the score by 1 point, which stays readable and does not saturate after two shifts (it would on 0 to 5).
- Stored preferences are whole numbers; computed rules (fairness) may return fractions.

### Rules return a verdict or no opinion
- Each rule returns `{ score, reason }` or **`null` (no opinion)**.
- Existing rules return **0 when violated and `null` when satisfied**. A satisfied hard rule must not return a high score, otherwise hard rules would inflate the result.
- Preference rules (future) return 1 to 10 for the shifts they care about and `null` elsewhere.

### "No opinion" is not a value
`null` is never compared on the scale: the rule simply drops out of the average. It only shows up when every rule abstains, and then the final score is the neutral 5. Returning 5 instead would dilute the average by however many unrelated rules happen to apply, so adding or removing rules would change who wins.

### Combining verdicts for one employee and shift
- Any rule returning 0 makes the final score **0**, whatever the others say.
- Otherwise the final score is the **weighted average** of the non-null scores. No opinions at all gives 5.
- Weights: default **1** per rule, configurable per rule type. Rules are combined in a fixed order (by rule id) so floating-point results are identical on every run (determinism, ADR-4a9d8da).

### Fairness is a rule
Fairness is implemented as one more rule in the same framework, not as a separate step:
- **Fairness score** = `clamp(5 + gap, 1, 10)` where `gap = expected shifts by now - shifts worked so far`. Manual assignments count as worked. How "expected by now" is computed, including vacations and the compensate checkbox, is defined in the next section. Exactly on target gives 5, 3 shifts behind gives 8, 2 ahead gives 3. It never returns 0, so it never blocks anyone by itself.
- **Weight: 2 by default**, a **company setting** that can be changed. A larger weight makes shift counts more even at the cost of preferences; a smaller weight does the opposite. This is the single knob for the fairness vs preference balance.
- **Fairness cap** (guarantee): an employee who is already **N shifts above expected** (default N = 2, a **company setting** that can be changed) gets 0 for further shifts as long as at least one other candidate remains. If every candidate is capped the cap is ignored for that shift, so the cap can never leave a shift empty. This bounds the spread between employees even if preferences are strong.

### Expected shifts, vacations and the compensate checkbox
Let **W** be the workable shifts in the calendar range (not closed by company rules, on working weekdays). For each employee **e**:
- **Window**: shifts of W between e's first shift and last shift (the whole range if not set).
- **Counting shifts** `C(e)`: the window minus the vacation shifts whose **compensate is off**. Vacation shifts with **compensate on count as owed**: they stay in `C(e)`.
- Scale factor `k = |W| / sum of C(e) over all employees`.
- **Expected by now** at shift t: `k * (number of e's counting shifts before t)`.
- **Target** (at the end of the range): `k * C(e)`.

Effect of the checkbox on one vacation:
- **Compensate off** ("okay to have fewer shifts"): the vacation shifts are not counting shifts. The employee's expected count does not grow during the vacation and the final target is smaller, so no debt builds up and the others share the work.
- **Compensate on** (default, "PTO taken into account"): the vacation shifts are counting shifts. While away the employee cannot work, but the expected count keeps growing, so the gap grows, the fairness score rises after the return, and the employee is picked more often around the PTO until the total is made up.

Example: 3 employees, 90 workable shifts, A has 10 vacation shifts.
- Off: `C(A) = 80`, `C(B) = C(C) = 90`, k = 90/260. Targets: A about 27.7, B and C about 31.2.
- On: `C = 90` for all, k = 1/3. Targets: 30 each. A can work only 80 shifts, so A needs 30 of them: more shifts around the PTO.

The same mechanism handles employees who start later or leave earlier (first/last shift): their window is shorter, so they get a proportionally smaller target. Settings per vacation, so one employee can have a compensated and an uncompensated vacation.

### Choosing an employee for a shift
Candidates with final score above 0 are ordered by **final score** (fairness already included), then by the fixed tie-break (last name, first name, id). There is no separate fairness step.

With no preference rules the only opinion is fairness, so behaviour equals plain fairness-based selection.

### Worked examples (fairness weight 2, preference weight 1)

| Employee | Opinions | Final score |
|---|---|---|
| A | preference 9 | 9 |
| B | none | 5 |
| C | preference 2 | 2 |
| D | preferences 9 and 1 | 5 |
| E | a rule says 0 | 0 |

Preference vs fairness for one shift:

| Employee | Preference | Fairness (gap) | Final |
|---|---|---|---|
| X | none | 8 (3 behind) | 8 |
| Y | 10 | 5 (on target) | (10 + 2x5) / 3 = 6.7 |
| Z | 10 | 2 (3 ahead) | (10 + 2x2) / 3 = 4.7 |

X gets the shift: being 3 shifts behind outweighs a top preference elsewhere. Z, who is ahead, loses even with the top preference.

A two-channel design (hard rules as plain yes/no, only preference rules scored) was considered and rejected: preference rules still need to abstain (e.g. "prefers nights" has no opinion on day shifts), so it would not remove the need for "no opinion".

### Other points
- The score and its reasons are returned with each assignment, so the preview and tile warnings can say why.
- Manual assignments ignore scores (they are locked); a score of 0 for a manual assignment shows the warning from ADR-fec8e13.

## Configuration

Scheduling settings are stored in the company config and editable in the company rules screen. Defaults: fairness weight **2**, fairness cap **2** shifts, weight of every other rule **1**. Per-rule-type weights follow the same mechanism for future preference rules.
