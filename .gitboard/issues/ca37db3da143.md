## Context

The app version (`package.json`) is written into saved data files (ADR-112163d) and must identify the deployed code. A manual bump per PR is easy to forget. We considered: deploy on version change, deploy on every push with a CI-enforced bump, tag-driven releases, and release-please.

## Decision

- Use **release-please** (`release-type: node`). It opens and maintains one release PR that bumps `package.json` `version` and updates `CHANGELOG.md`. Normal PRs never edit the version by hand.
- Merging the release PR creates the tag (`vX.Y.Z`) and the GitHub Release.
- **GitHub Pages is deployed only from a release** (a deploy job in the same workflow, gated on `release_created`), so the live site always matches a version. Separate story.
- **Conventional Commits are required.** PRs are squash-merged, so the **PR title** is the commit message and is validated in PR checks (`amannn/action-semantic-pull-request`). Allowed types: feat, fix, perf, refactor, docs, test, build, ci, chore, revert. `feat` bumps minor, `fix`/`perf` patch, `!` or `BREAKING CHANGE` major (minor while below 1.0).
- `.gitboard/`-only commits pushed straight to `main` use `chore:` and do not trigger a release.

## Consequences

- No forgotten bumps and a free changelog. The version moves only when the release PR is merged.
- `main` can be ahead of the live site between releases.
- PR titles need `feat:`/`fix:` prefixes (documented in CLAUDE.md).
- PRs opened by the default `GITHUB_TOKEN` do not trigger CI, so the release PR does not run checks unless a PAT or GitHub App token is used. Accepted for now (the release PR only changes version and changelog).
- Repo setting needed: Actions may create pull requests.

## Acceptance Criteria

- [x] release-please chosen over manual bump and tag-driven releases
- [x] Conventional Commit PR titles enforced in PR validation
- [x] Deploy only from releases
