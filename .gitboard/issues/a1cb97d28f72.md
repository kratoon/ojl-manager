## Context

Each shift (date + day or night) has **two employees** instead of one, and the schedule follows a repeating pattern for 8 employees. This builds on ADR-fec8e13 (shifts and locks), ADR-86a9b67 (rules) and ADR-aaa3ccd (scores).

## The pattern (confirmed answers)

- **Fixed pairs**: every employee is in a pair with one other employee. Pairs are configured on the employee setup page. The pair always works the same shifts together. The pattern can be broken occasionally (PTO, sick days).
- **Blocks**: a week has three blocks of consecutive days: **MON+TUE** (short, 2), **WED+THU** (short, 2), **FRI+SAT+SUN** (long, 3). Counting blocks from an anchor Monday gives one endless sequence: short, short, long, short, short, long, ...
- Inside a block the pair works the **same kind** of shift (all day or all night).
- A pair works **every other block**, and alternates **day, night, day, night** on the blocks it works.
- With 4 pairs (8 employees): each block is worked by two pairs, one on the day shift and one on the night shift. Pairs A and C share the even blocks and pairs B and D share the odd blocks; A and C always take opposite kinds, as do B and D.
- Each employee therefore works 7 shifts per 14 days (2 + 3 + 2) and alternates short/long blocks and day/night blocks.

Formal definition. Let `n` = block number counted from the anchor Monday (0, 1, 2, ...; three blocks per week). Pair position `p` is 0 to 3 (A to D). The pair works block `n` when `n mod 2 = p mod 2`. With `m = floor(n / 2)`, it works the **day** shift when `(m + floor(p / 2))` is even, otherwise the **night** shift.

First two weeks with 4 pairs (D = day, N = night):

| Block | Days | A | B | C | D |
|---|---|---|---|---|---|
| 0 | MON+TUE | D | | N | |
| 1 | WED+THU | | D | | N |
| 2 | FRI+SAT+SUN | N | | D | |
| 3 | MON+TUE | | N | | D |
| 4 | WED+THU | D | | N | |
| 5 | FRI+SAT+SUN | | D | | N |

## Decision

- **Seats**: company setting `seatsPerShift`, default 2. Assignments are a list of up to that many entries per shift (`{ employeeId, source }`), the lock is per seat. One employee cannot take both seats of a shift. Existing single assignments migrate to one-element lists.
- **Fairness**: each shift needs two people, so the scale factor is multiplied by the number of seats (`k = seats * |W| / sum of counting shifts`).
- **Neighbour rules** (max in a row, day/night mixing) ask whether the employee works that shift.
- **Pattern is a soft preference** in the score framework: an employee whose pair is on pattern for this shift scores 10, everybody else 1, with a configurable weight (default 4, fairness stays 2). Hard rules (vacation, first/last shift, exclusions, max in a row, mixing) still win, so PTO or sick days break the pattern and the generator fills the free seat with the best available employee. The pattern is a pure function of the date, so a pair returns to it automatically afterwards.
- **Pairs and pair order**: pair positions A to D come from sorting the pairs by their members' names (last name, first name, id), so the rotation is deterministic. The anchor Monday (start of block 0) is a company setting.
- **Pairing check before generating**: every employee must have a partner, except that **one** employee may be unpaired when the number of employees is odd (7 employees: 3 pairs + 1 single). Regenerate is disabled until this holds. An unpaired employee takes the next free position; the second seat of their shifts is filled by the generator.
- **Sick days**: recorded like PTO (an absence entry on the employee, with the compensate checkbox deciding whether missed shifts are made up).
- A **manual assignment** locks a seat as before; the pattern never overwrites it.
